# hu_accomponist (Flutter app)

The iOS app. You pick a score or a built-in exercise, play it on a real
instrument, and get feedback on each phrase.

It talks to two other parts of the project:

- **`native_ffi/`** (Rust): listens to the microphone and detects notes.
  See `native_ffi/README.md`.
- **`backend/`** (Django): IMSLP search and PDF download, the quiz, and the
  feedback judge.

## Running it

1. Start the backend:
   ```sh
   cd backend
   docker compose up -d
   export DYLD_FALLBACK_LIBRARY_PATH="$(brew --prefix vips)/lib:$DYLD_FALLBACK_LIBRARY_PATH"
   python3 manage.py runserver 0.0.0.0:8000
   ```
   The app finds the server by itself over Bonjour (mDNS), so you don't need
   to type in an IP address.
2. Run the app:
   ```sh
   cd frontend
   flutter devices                    # lists simulators and connected phones
   flutter run -d "iPhone Air"        # a simulator
   flutter run -d Kelvin              # a real phone, matched by the start of its name
   ```
   A phone has to be unlocked and either plugged in or on the same Wi-Fi.
   The start of a device's name is enough. Typing the full phone name can
   fail to match: `Kelvin’s iPhone` uses a curly apostrophe.
   - On a phone's first install, trust the developer certificate under
     Settings → General → VPN & Device Management.
   - Allow the microphone when asked.
   - Signing uses development team `QTTDV89898`, set in the Xcode project.

## Practising with an exercise

This is the way to test with a real instrument today.

1. Spin the vinyl to **Practice**.
2. Tap **"or practise an exercise"**. It's also in the settings drawer.
3. Pick an exercise (C major scale, C major arpeggio or Twinkle), a tempo
   (60/80/100 bpm) and a starting octave. Higher octaves are detected more
   accurately.
4. Tap the mic. A 4-beat count-in follows, shown on screen and felt as
   haptics. **Play the first note on the beat after "4"**, and keep time
   with the pulsing dot.
5. After each bar a feedback card appears and the companion reacts.

## Playing along with a score

1. Pick a score from the library (Search), e.g. Für Elise.
2. Tap the mic. The first time, choose a tempo (from the written one: Slow
   60%, Steady 80%, As written) and, on a piano score, which hands. The chip
   at the top of the score changes them later.
3. A count-in of one bar follows. Start on the first note.
4. As you play, each note turns **soft green** when it was right and **red**
   when it was a wrong key, missed, or badly early or late. The notes due now
   sway a little, and a note hops as it is heard. A line at the top says what
   went wrong ("Played D instead of D♯ · bar 12"). The page scrolls to keep
   the next note in view.
5. Every few seconds the backend's verdict on the last phrase comes back as
   the feedback card, and can turn more notes red.

The score follows your tempo, so you don't have to keep the written one, and
waits if you stop.

Recording a **PDF score** is still refused: the backend step that reads notes
off a PDF (`/api/score/process`) does not work yet. MusicXML scores from the
library work.

## Navigation, sign-in and the tutorial

`main.dart` shows the boot splash, then `AuthGate`: the login page when nobody
is signed in, otherwise `AppShell`. The session token lives in the platform
keychain (`flutter_secure_storage`), so the app opens straight into Home
on every launch until Log Out. A stored session is trusted offline; only the
server answering 401 signs the person out.

`AppShell` hosts seven pages (Home, Practice, Search, Shelf, Quiz, Hum,
Settings, in `features/shell/disk_pages.dart`) rather than pushing them, and
opens on Home. Practice is built the first time it is shown and kept after
that; the others are rebuilt on each visit, as they were when they were
pushed routes. A hosted page hides its own back and close buttons
(`InShellPage`), and a page that hands back a score (Search, the Shelf, Home's
Continue) goes through `ShellScope`'s `openScore` instead of popping.

The bottom bar (`DiskBar`) is three spinning records: the current page's in
the middle with a gold ring, its neighbours either side. Drag along it to
browse (it wraps, and a fling can pass several), tap a side disk to jump, hold
for the disk drawer (`DiskDrawer`: haptic, dimmed and blurred screen, the
disks scatter over the lower screen). `MiniDisk` draws the vinyl; the label
turns at 33⅓ rpm while the lighting stays put.

The first-run tutorial (`TutorialOverlay`) cuts a hole over the disks so the
gestures are tried on the real thing. The swipe step shows an animated
example and only moves on when `DiskBar.onSwiped` reports a drag that changed
the page (a tap or the drawer does not count). Finishing or skipping sets
`hasCompletedOnboarding`; Settings can replay it.

`features/home/home_page.dart` is the dashboard: the last score played (from
`ShelfManager`, the shelf's own record) with Continue Practicing, two earlier
ones, and a card for every other page.

## Practice feedback

In an exercise, `ExerciseDisplay` marks the note(s) to play now in red, from
the same clock that drives the count-in. When a bar is judged
(`ExerciseSession.receive`), `PracticeNotice.fromReport` turns the generator's
findings into notices. A finding is placed on a written note only when its
`details.note_id` names one (pitch, rhythm, articulation, missing notes);
tempo drift and extra notes are about the bar, and the wording is always the
generator's. One bubble at a time pops up beside the note and dismisses
itself, the notes keep a badge, and the speech-bubble button lists everything
said this run.

For a *score*, the notes come from the score itself:
`assets/osmd/score_timeline.js` reads them off OSMD's parsed score (repeats
played out, ties joined, grace notes just before their note, timed at the
written tempo, first instrument only) and the page posts them as a
`timeline` message. Each note's id is its place in that timeline, which is
how Rust, the backend and the page all refer to it.

| File | Role |
|---|---|
| `features/practice/score_timeline.dart` | The timeline, laid out at a tempo for some hands. Bars are grouped into phrases of 4 s or more for the backend. |
| `features/practice/score_practice_session.dart` | One run through a score: Rust (with `follow_tempo`), count-in, live judging, phrases to the backend. |
| `features/practice/live_judge.dart` | Right or wrong per note, from Rust's records as they arrive; which notes are due; the backend's verdicts on top. |
| `features/practice/score_practice_sheet.dart` | Tempo and hands. |
| `assets/osmd/osmd_viewer.html` → `OSMDBridge.live` | Colours noteheads (a chord member by its rank in pitch), sways due notes, hops played ones, keeps the next note in view; all re-applied after every re-render (zoom, rotation). |

The store-review URLs and support email are in `config/app_constants.dart`
and can be set at build time, e.g.
`flutter build ios --dart-define=PRIVACY_POLICY_URL=https://...`. The
defaults are placeholders.

Imports use `package:hu_accomponist/...` everywhere, so moving a file only
means updating the imports that name it.

## How a recording becomes feedback

```
tap mic
  └─ Audio_Native.prepare()          iOS: microphone permission + audio session (AppDelegate.swift)
  └─ Exercise_Session.prepare()
       ├─ Rust_Session.load()        initSession(): tells Rust which notes to expect
       └─ 4-beat count-in
  └─ Audio_Native.begin()            start_recording() → Rust opens the mic; a failure is shown, not recorded over
       └─ every second: Audio_Native.problem()   a silent mic, a stalled stream, processing that fell behind

Rust hears notes ──notesStream()──▶ Draggable_Recorder_Button
                                       └─ ExerciseSession.onRustBatch()
                                            └─ Phrase_Assembler: groups entries into bars
                                                 └─ Phrase_send2_server → POST /api/feedback/phrase
                                                      └─ report ─▶ Phrase_Feedback_Pill + Practice_Companion

tap mic again
  └─ Audio_Native.end() + getUserData() (waits until Rust has sent the last note)
  └─ ExerciseSession.finish()        getUserData() recovers a note still sounding; remaining bars are sent
```

A bar is sent once its last note ends, or once you move on to the next bar.
The second case means a bar is still judged when its last note was never
heard, and the unheard notes are reported as missed.

| File | Role |
|---|---|
| `features/practice/Exercise.dart` | The exercises, and the note layout for a tempo and octave. It produces both Rust's `PieceData` and the backend's `expected_notes`, so the two always agree. |
| `features/practice/Exercise_Session.dart` | One run: load, count-in, send bars in order, report results. |
| `features/practice/Phrase_Assembler.dart` | Groups Rust's per-frame entries into bars, one entry per note. |
| `features/practice/Exercise_Display.dart` / `Exercise_Picker.dart` | The exercise screen and the chooser. |
| `features/practice/Phrase_Feedback.dart` | The good/fair/off mood bands (80+, 55+, below). The companion, recorder glow, drawer and card all use it. |
| `integrations/audio/Rust_Bridge.dart` | Starts the flutter_rust_bridge runtime (see below). |
| `integrations/audio/Rust_Session.dart` | `initSession` and `getUserData` wrappers. |
| `integrations/audio/Audio_Native.dart` | Mic permission, start/stop and error status through `dart:ffi` and the `audio_session` channel. |
| `integrations/feedback/Phrase_send2_server.dart` | Converts Rust notes into the backend's format and sends each phrase. |

## iOS native build setup — keep these

Getting Rust to work on both the simulator and a real phone needed the
settings below. Each one breaks something specific if removed.

| Setting | Where | If removed |
|---|---|---|
| `EXCLUDED_ARCHS[sdk=iphonesimulator*] = x86_64` | Xcode build settings, all configs | Simulator build fails: the Rust library is arm64 only |
| `OTHER_LDFLAGS[sdk=iphoneos*] = -force_load $(PROJECT_DIR)/libnative_ffi.a` and the `iphonesimulator` equivalent with `libnative_ffi_sim.a` | Runner target | Wrong library linked for the platform, or bridge functions left out of the app |
| The `.a` files **not** in "Link Binary With Libraries" | Runner target | Phone build fails, because it links the simulator library |
| `DEAD_CODE_STRIPPING = NO` | Runner Release and Profile | Release builds remove the Rust bridge: the app starts but Rust never loads |
| `DART_EXPORT` on `start_recording` / `stop_recording` / `recording_status` / `recording_message` | `ios/recording_bridge.c` | Release builds hide the functions, and the mic never starts |
| `AVAudioSession` set to play-and-record, and the permission request | `ios/Runner/AppDelegate.swift`, called by `Audio_Native.prepare()` | The mic opens but delivers silence (the default session cannot record), or permission is never asked |
| `ExternalLibrary.process()` on iOS | `Rust_Bridge.dart` | "Failed to load dynamic library native_ffi.framework" |

Only `ios/recording_bridge.c` is compiled. The copy in `ios/Runner/` is
unused.

## Reading the terminal

The app logs with a `[Diagnostics]` prefix. The useful lines:

| Line | Meaning |
|---|---|
| `rust: bridge initialized` | Rust loaded. `bridge unavailable` means the bindings and the library don't match (rebuild, see `native_ffi/README.md`). |
| `audio: native capture bridge connected` | The mic functions were found. |
| `rust: loaded "C major scale" (16 notes)` | Rust knows what to listen for. |
| `phrase N detected by Rust` | A batch arrived from Rust. |
| `bar N: X heard / Y written` | A bar is being sent. |
| `phrase N OK: HTTP 200 … overall=…` | The backend judged it. |
| `discovery: TIMED OUT` | The backend wasn't found. Check it's running. |

## Troubleshooting

- **`Flutter.framework/Flutter does not exist, cannot thin`**: Flutter's own
  engine cache is damaged. Run `flutter precache --ios --force`, then delete
  this project's folder under `~/Library/Developer/Xcode/DerivedData/`.
- **`NonUniqueNameException` when starting Django**: another server is still
  advertising itself. Stop it, or wait about a minute for the old
  announcement to expire.
- **"Could not find the accompaniment server"**: the backend isn't running,
  or the phone isn't on the same network.
